# Explore With Me

Это мой дипломный проект на Java 21 и Spring Boot. На втором этапе я разделила основное приложение на несколько микросервисов. Раньше вся основная логика была в одном приложении, а теперь каждый сервис отвечает за свою часть.

## Как я разделила проект

В папке `core` находятся шесть сервисов:

- `user-service` — работа с пользователями;
- `event-service` — создание, изменение и поиск событий;
- `request-service` — заявки на участие в событиях;
- `category-service` — категории;
- `compilation-service` — подборки событий;
- `comment-service` — комментарии.

Для статистики остался отдельный `statistics-service`. Общие DTO и классы, которые нужны нескольким сервисам, я оставила в модуле `common`.

У каждого бизнес-сервиса своя база PostgreSQL. Например, сервис событий хранит ID автора, но не хранит у себя все данные пользователя. Когда они нужны, он обращается к `user-service`.

Сервисы общаются через OpenFeign. Чтобы не указывать адрес каждого сервиса вручную, я использовала Eureka. Настройки они получают из Config Server, а все внешние запросы проходят через Gateway на порту `8080`.

В проекте для этого есть три инфраструктурных модуля:

- `infra/discovery-server` — Eureka;
- `infra/config-server` — общие настройки;
- `infra/gateway-server` — входная точка для запросов.

## API

Все запросы из Postman отправляются на `http://localhost:8080`. Gateway перенаправляет их в нужный сервис. Например, `/admin/users` относится к пользователям, `/events` — к событиям, `/categories` — к категориям, `/compilations` — к подборкам, `/users/{userId}/requests` — к заявкам, а запросы с `/comments` — к комментариям. Для статистики используются `/hit` и `/stats`.

Спецификации внешнего API лежат в корне проекта:

- [Основной сервис](ewm-main-service-spec.json)
- [Статистика](ewm-stats-service-spec.json)

### Внутренние запросы

Сервисам также нужно получать данные друг от друга. Для этого я добавила внутренние запросы, которые вызываются через Feign. Они не предназначены для обращения через Gateway.

| Сервис | Запрос | Для чего |
| --- | --- | --- |
| `user-service` | `GET /internal/users/{userId}` | Найти пользователя |
| `user-service` | `GET /internal/users?ids=...` | Получить сразу несколько пользователей |
| `event-service` | `GET /internal/events/{eventId}` | Найти событие |
| `event-service` | `GET /internal/events/short?ids=...` | Получить несколько событий |
| `event-service` | `GET /internal/events/exists-by-category/{categoryId}` | Проверить, используется ли категория |
| `request-service` | `GET /internal/requests/confirmed-count?eventId=...` | Узнать число подтверждённых заявок |
| `request-service` | `GET /internal/requests/confirmed-counts?eventIds=...` | Получить число заявок сразу для нескольких событий |
| `category-service` | `GET /internal/categories/{categoryId}` | Найти категорию |
| `category-service` | `GET /internal/categories?ids=...` | Получить несколько категорий |

В списках событий я старалась получать связанные данные сразу по нескольким ID, а не делать отдельный запрос для каждого события.

## Настройки и обработка ошибок

Настройки сервисов находятся в `infra/config-server/src/main/resources/config/`. Маршруты Gateway я прописала в файле `gateway-server.properties`. В каждом сервисе есть свой `src/main/resources/application.properties` с настройками подключения к Eureka и Config Server.

Если один из сервисов временно недоступен, приложение не должно полностью переставать работать. Для внутренних запросов я использовала Circuit Breaker и повторные попытки. При удалении пользователя `user-service` проверяет существование его событий и заявок: если ответ от зависимого сервиса получить нельзя, удаление **не выполняется**, а возвращается `503`. Проверять отсутствие зависимостей как `false` в таком случае опасно. Например, если не отвечает сервис заявок, там, где это допустимо, количество подтверждённых заявок возвращается как `0`. Если недоступна статистика, просмотр событий не должен из-за этого ломаться. А если для события не получается получить обязательные данные пользователя или категории, возвращается ошибка `503`, чтобы не показывать неправильную информацию.

## Третий этап: рекомендации

На третьем этапе я добавила три сервиса для персональных рекомендаций:

- `collector` принимает события VIEW, REGISTER и LIKE через gRPC и пишет Avro в Kafka;
- `aggregator` читает действия и инкрементально вычисляет сходство мероприятий;
- `analyzer` сохраняет действия и сходства в PostgreSQL и отвечает по gRPC.

Kafka использует топики `stats.user-actions.v1` и `stats.events-similarity.v1`.
Они создаются в `kafka-init` до запуска сервисов рекомендаций.

В локальном Docker Compose рекомендательные сервисы запускаются вместе с
остальными (`docker compose up -d --build`), без отдельного профиля.
Aggregator при перезапуске пересчитывает состояние из всей истории
`stats.user-actions.v1`. Поэтому для **учебного** стенда у топика
устанавливается `retention.ms=-1`: Kafka не удаляет историю по времени,
но она продолжает занимать место на диске. Запуск нескольких экземпляров
Aggregator одновременно **не поддерживается**. Если какая-либо часть
истории Kafka была удалена до включения этого режима, полный пересчёт
не гарантируется и требуется отдельное восстановление данных.

При обычной обработке Aggregator публикует коэффициенты и фиксирует
входящий offset в одной Kafka-транзакции. Analyzer читает только
подтверждённые записи; невалидные сообщения направляются в топики
`stats.user-actions.v1.DLT` и `stats.events-similarity.v1.DLT`, а
временные ошибки БД повторяются. DLT нужно проверять отдельно: появление
там сообщений означает, что часть исходных событий не вошла в расчёт.

**Ограничение учебной реализации:** пока Aggregator восстанавливается
повторным чтением истории, могут публиковаться промежуточные значения
сходства. До завершения восстановления рекомендации могут быть временно
неактуальными. Для production потребуется устойчивый checkpoint/снимок
состояния и согласованная версия коэффициентов.

У Analyzer есть три gRPC-метода: `GetRecommendationsForUser`,
`GetSimilarEvents` и `GetInteractionsCount`. Для расчёта рейтинга используется
сумма максимальных весов взаимодействий пользователей с мероприятием.

В публичном API есть `GET /events/recommendations`, а `GET /events/{id}`
регистрирует VIEW. Для этих запросов требуется заголовок `X-EWM-USER-ID`.
`PUT /events/{eventId}/like` допускается только после проведения мероприятия
и для участника с подтверждённой заявкой. В ответах на события возвращается
`rating`, а не старое поле `views`.

При создании заявки `request-service` сохраняет REGISTER в отдельной таблице
`registration_action_outbox` в **той же транзакции**, что и заявку. После коммита срабатывает асинхронный обработчик отправки в Collector, не
блокирующий HTTP-ответ; при недоступности Collector планировщик повторяет
доставку из outbox с интервалом 10 секунд. Повторная доставка допустима, поскольку
Aggregator и Analyzer учитывают только максимальный вес действия.

## Как запустить

Для проекта нужны JDK 21, Maven и Docker Compose.

Сначала в корневой папке собираю проект:

```bash
mvn clean install -Pcheck
```

После сборки запускаю контейнеры:

```bash
docker compose up -d --build
# Проверка всех контейнеров, включая Kafka и рекомендательные сервисы:
docker compose ps
```

Сначала нужна сборка Maven, потому что Dockerfile использует собранные JAR-файлы из папок `target`. Данные PostgreSQL сохраняются в Docker volumes. В этом `docker-compose.yml` используется по одному экземпляру каждого сервиса. Для них заданы стабильные `EUREKA_INSTANCE_ID`: это снижает риск накопления старых Eureka-регистраций при пересоздании контейнера с новым случайным портом. При горизонтальном масштабировании ID **обязательно** должны быть разными для каждой реплики. Старые регистрации от предыдущего варианта могут сохраняться в Eureka до окончания их lease; вручную удалять их при обычном запуске не требуется.

При подтверждении заявок с ограниченным числом мест `request-service` использует транзакционную блокировку PostgreSQL по идентификатору мероприятия, чтобы параллельные запросы не заняли одно последнее место. Запрос со статусом `REJECTED` разрешён и при полном событии. Для списков события читаются порциями, применяются стабильные правила сортировки и точная пагинация по смещению `from`; при сортировке по числу просмотров необходимо получить оценки всех подходящих событий — это ограничение глобальной сортировки.

## Как проверить

Для проверки исходного API использую три коллекции Postman:

1. `postman/ewm-main-service.json` — основной API;
2. `postman/ewm-stat-service.json` — статистика;
3. `feature.json` (также `feature_test.json`) — исходные тесты комментариев (7 запросов, №16–22).

Все запросы должны идти через Gateway на порт `8080`. **Важно:** `postman/feature.json` — вспомогательная коллекция `Comments Feature Tests Copy`, которая отличается от исходных тестов. Её нельзя использовать вместо `feature.json` для подтверждения требований ТЗ. Оригинальные Postman-файлы не меняются.

Для проверки сборки, модульных тестов, Checkstyle и SpotBugs можно выполнить:

```bash
mvn clean verify -Pcheck
```

Отдельно проверяю, как приложение работает при отключении сервисов. Сначала запускаю всё, потом останавливаю сервисы по одному и проверяю запросы, которые от них не зависят. В конце оставляю из бизнес-сервисов только `event-service` вместе с нужной инфраструктурой. После проверки запускаю остальные сервисы обратно.

Второй этап выполнялся в ветке `microservices` и был принят ревьювером. Слияние и публикация изменений выполняются только после соответствующего разрешения.

## Проверка третьего этапа

Перед сдачей выполняю `mvn -B -ntp -Pcheck clean verify` из корня проекта.
Затем через Gateway проверяю `GET /events`, сортировку `RATING`, запрос
`GET /events/{id}` с заголовком и без него (400), наличие `rating` без
`views`, `GET /events/recommendations` и запрет преждевременного лайка (400).
Также проверяю цепочку Collector → Kafka → Aggregator → Kafka → Analyzer
и повторную доставку REGISTER после временной недоступности Collector.
Данные PostgreSQL и Kafka хранятся в Docker volumes; при проверках их
не нужно удалять. Официальные Postman-коллекции не изменяются.

Разработку третьего этапа веду в ветке `recommendations`; после проверки
подготавливаю PR в `main`.

# Explore With Me

Это дипломный проект на Java 21 и Spring Boot. На втором этапе я разделила основное приложение на микросервисы.

## Какие сервисы есть в проекте

| Модуль | За что отвечает |
|---|---|
| `core/user-service` | Пользователи |
| `core/event-service` | Создание, изменение и поиск мероприятий |
| `core/request-service` | Заявки на участие в мероприятиях |
| `core/category-service` | Категории |
| `core/compilation-service` | Подборки событий |
| `core/comment-service` | Комментарии |
| `statistics-service/statistics-service-server` | Сохранение и получение статистики просмотров |
| `infra/discovery-server` | Eureka: помогает сервисам находить друг друга |
| `infra/config-server` | Хранит общие настройки сервисов |
| `infra/gateway-server` | Принимает внешние запросы на порту `8080` |
| `common` | Общие DTO и классы, которые нужны нескольким сервисам |

У каждого бизнес-сервиса своя база PostgreSQL. Например, сервис мероприятий хранит идентификатор автора, а информацию о пользователе получает из `user-service`.

Сервисы обращаются друг к другу через OpenFeign. Eureka помогает найти нужный сервис. В списках данные о пользователях и категориях запрашиваются сразу для нескольких мероприятий, чтобы не отправлять запрос для каждого по отдельности.

## API

Внешние запросы нужно отправлять на `http://localhost:8080`. Gateway направляет их в нужный сервис:

- `/admin/users/**` — пользователи;
- `/events/**`, `/admin/events/**`, `/users/{userId}/events/**` — мероприятия;
- `/users/{userId}/requests/**` и `/users/{userId}/events/{eventId}/requests/**` — заявки;
- `/categories/**`, `/admin/categories/**` — категории;
- `/compilations/**`, `/admin/compilations/**` — подборки;
- `/events/{eventId}/comments/**`, `/users/{userId}/comments/**`, `/admin/comments/**` — комментарии;
- `/hit`, `/stats` — статистика.

Спецификации внешнего API находятся в файлах [основного сервиса](ewm-main-service-spec.json) и [статистики](ewm-stats-service-spec.json).

### Внутренние запросы между сервисами

Эти адреса используются внутри Docker-сети через OpenFeign. Снаружи через Gateway они не открываются.

| Сервис | Внутренний запрос | Для чего нужен |
|---|---|---|
| `user-service` | `GET /internal/users/{userId}` | Получить пользователя |
| `user-service` | `GET /internal/users?ids=...` | Получить нескольких пользователей |
| `event-service` | `GET /internal/events/{eventId}` | Получить данные мероприятия |
| `event-service` | `GET /internal/events/short?ids=...` | Получить несколько мероприятий |
| `event-service` | `GET /internal/events/exists-by-category/{categoryId}` | Проверить, используется ли категория |
| `request-service` | `GET /internal/requests/confirmed-count?eventId=...` | Узнать число подтверждённых заявок |
| `request-service` | `GET /internal/requests/confirmed-counts?eventIds=...` | Получить количества для нескольких мероприятий |
| `category-service` | `GET /internal/categories/{categoryId}` | Получить категорию |
| `category-service` | `GET /internal/categories?ids=...` | Получить несколько категорий |

## Настройки

Конфигурация сервисов находится в `infra/config-server/src/main/resources/config/`. Маршруты Gateway указаны в `gateway-server.properties`.

В папке каждого сервиса есть `src/main/resources/application.properties`: там настроено подключение к Eureka и Config Server.

Для межсервисных вызовов используется Circuit Breaker. Если сервис заявок недоступен, количество подтверждённых заявок временно будет `0`. Если не работает статистика, просмотры также будут `0`. Клиент статистики выбирает экземпляры по очереди и повторяет временно неудачные GET-запросы. Для временных ошибок `5xx` при внутренних GET-запросах настроены три попытки с интервалом 3 секунды. Если недоступны данные пользователя или категории, мероприятие нельзя показать полностью, поэтому возвращается ошибка `503`.

## Как запустить

Нужны JDK 21, Maven и Docker Compose. Собрать проект можно через встроенный Maven в IntelliJ IDEA с профилем `check`.

Сборка из терминала в корневой папке проекта:

```bash
mvn clean install -Pcheck
```

После успешной сборки можно запустить контейнеры:

```bash
docker compose up -d --build
docker compose ps
```

Dockerfile использует JAR-файлы из `target`, поэтому Maven нужно запустить до Docker Compose. Данные PostgreSQL сохраняются в Docker volumes.

## Как проверить второй этап

Все внешние запросы проходят через Gateway: `http://localhost:8080`.
Для второго этапа нужны **три группы Postman-тестов**:

1. `postman/ewm-main-service.json` — основной API;
2. `postman/ewm-stat-service.json` — API статистики;
3. `postman/feature.json` — разработанные для дополнительной функциональности тесты комментариев.

В корне также оставлен исходный `feature_test.json` с отдельными проверками комментариев. Он не заменяет полную коллекцию `postman/feature.json`.
Все перечисленные JSON-файлы сохранены без изменений.

### Проверка отказоустойчивости

1. Запустите все сервисы и проведите три серии Postman-тестов.
2. Останавливайте **по одному бизнес-сервису**, выполняйте запросы, не зависящие от него, затем запускайте остановленный сервис обратно.
3. Для финальной проверки оставьте работающим `event-service` и нужные ему `event-db`, `gateway-server`, `discovery-server`, `config-server`. Другие бизнес-сервисы временно остановите. Запросы, не требующие данных других микросервисов, должны продолжить работать. Если нужны данные недоступного сервиса (например, сведения о категории или пользователе), допускается явный ответ об их недоступности, а не некорректные данные.
4. Возобновите работу всех остановленных сервисов после проверки.

Например, если недоступен `request-service`, сервис мероприятий возвращает `0` подтверждённых заявок там, где это допустимо. Если недоступен сервис статистики, отсутствие просмотров не должно полностью останавливать работу мероприятий. Для временных серверных ошибок внутренних GET-запросов предусмотрены повторные попытки и Circuit Breaker.

В тестах надёжности специально проверяется поведение **при отказе**, поэтому полную обычную Postman-коллекцию не нужно запускать, когда критические сервисы отключены.

### Сборка

Для обычной полной сборки исходников, модульных тестов, Checkstyle и SpotBugs используется:

```bash
mvn clean verify -Pcheck
```

В проекте сохранён дополнительный профиль `coverage` с порогами JaCoCo. Он не входит в требования, приведённые для второго этапа, и применяется отдельно при необходимости; пороги не изменялись.

Работа над вторым этапом ведётся в ветке `microservices`. После проверки создаётся PR из `microservices` в `main` и ссылка передаётся ревьюверу. Merge выполняется **после одобрения ревьювера**.
